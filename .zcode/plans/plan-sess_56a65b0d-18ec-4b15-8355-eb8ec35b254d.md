## Plan: Camera-view image planes with dataset photo + splat render + 3-way toggle

Extend `static/cam_viewer/cam_viewer.html` so each camera's image plane can show either the dataset photo or a TripoSplat-splat render of that camera's viewpoint (or both side-by-side), switched by a 3-way control. Splat views are pre-rendered to offscreen textures at load time using Spark.js's `renderTarget` API.

### New query param
- `?splat=<url>` — URL of the TripoSplat-generated splat file (PLY/Splat). Optional: when absent, the "splat" and "both" modes show a placeholder (gray plane with "no splat" text); dataset-photo mode is unaffected. Loaded via `new SplatMesh({ url })`, awaited with `await splat.initialized`.

### Spark.js offscreen rendering setup
- Add `@sparkjsdev/spark` to the importmap (same version as viewer.html: `https://unpkg.com/@sparkjsdev/spark@2.0.0/dist/spark.module.js`).
- Create a **second** `WebGLRenderer` (offscreen, not added to DOM) OR reuse the main renderer — reuse the main renderer to avoid a second WebGL context. Construct a **second** `SparkRenderer` with the `target` option for offscreen capture:
  ```js
  const offSpark = new SparkRenderer({ renderer, target: { width: RENDER_W, height: RENDER_H } });
  ```
  Add `offSpark` to a **separate** `THREE.Scene` (`splatScene`) that contains only the splat mesh + splatRoot (NOT the cameras/points/grid). This keeps the splat render clean (no frustums/axes in the captured views).
- `RENDER_W × RENDER_H` = fixed small offscreen size (e.g. **512×384** by default), aspect set per-camera from `w/h` so the splat view matches the photo's aspect. Since `SparkRenderer.target` is fixed-size at construction, I'll size it to a square **768×768** and render each camera with an offscreen `PerspectiveCamera` whose aspect = `w/h`; the target is square so any aspect fits. (The splat fills whatever the camera frustum is; a square target + camera aspect gives correct proportions.) Actually simplest: fixed **768×768** target, offscreen camera `aspect = w/h`, FOV from `camera_angle_x`. Document this.

### Splat pose
- **Identity pose in the camera world frame** (per user choice): the splat is added to `splatScene` at the origin with **no yaw/X-flip** (`splatRoot.rotation = 0`), on the assumption the TripoSplat splat was generated from this dataset and lives in the same world frame as the mvs cameras.
- After `await splat.initialized`, call `splat.getBoundingBox()` (local) / `Box3().setFromObject(splatRoot)` (world) to get the splat's extent — used only for an optional status line, not for posing.

### Per-camera offscreen render
For each camera (across all 64 frames), build an offscreen `PerspectiveCamera`:
- **Pose**: reuse `nerfstudioC2WToThreeJS(frame.transform_matrix)` (respects `flipYZ`) — same world matrix as the frustum node, so the splat view is exactly what that camera sees.
- **Intrinsics**: `fov = camera_angle_x * 180/π` (horizontal FOV), `aspect = w/h`, `near = 0.01`, `far = 1000`. Set via `camera.setFocalLength`? No — use `PerspectiveCamera(fov, aspect, near, far)` with `fov` from `camera_angle_x` (horizontal) → Three.js `PerspectiveCamera.fov` is **vertical**, so compute `verticalFov = 2*atan(tan(angleX/2) / aspect)` and set `camera.fov = verticalFovDeg`, `camera.aspect = w/h`, `updateProjectionMatrix()`.
- Apply the c2w: `offCam.matrixAutoUpdate = false; offCam.matrix.copy(c2w); offCam.matrixWorldNeedsUpdate = true;` (same technique as frustum nodes). Note: Three.js camera looks down its local -Z, and `nerfstudioC2WToThreeJS` already converts OpenCV (+Z fwd) → Three.js (-Z fwd), so this is consistent.

Render loop (one-time, at load, after splat initialized):
```js
for (const { frame, split } of allCameras) {
  const offCam = makeOffscreenCam(frame);
  const target = offSpark.renderTarget({ scene: splatScene, camera: offCam });
  // target.texture is a THREE.Texture — store per-camera
  splatTextures.set(frameKey, target.texture);
}
```
Store each `target.texture` in a `Map` keyed by `(split, cam_idx)`. The render target is persistent (owned by `offSpark`), so its `.texture` stays valid; I render each camera once and keep the texture reference.

> Performance: 64 renders × 768². Each `renderTarget` is one `renderer.render` call with splat sort. Estimated ~1-2s total. Done once. Show progress in the loading label ("Rendering splat views (i/n)…").

### Image plane material changes
Currently each image plane is one `Mesh` with one `MeshBasicMaterial({ map: photoTex })`. To support 3 modes (photo / splat / both), change the plane to a **`ShaderMaterial`** (or use Three.js built-in multi-texture) that blends two textures based on a `uMode` uniform:
- `uMode = 0`: show `uPhotoTex` only
- `uMode = 1`: show `uSplatTex` only
- `uMode = 2`: side-by-side — sample `uPhotoTex` for `uv.x < 0.5`, `uSplatTex` for `uv.x >= 0.5` (left half = photo, right half = splat). A thin divider line at `uv.x = 0.5`.

Shader (fragment):
```glsl
uniform sampler2D uPhotoTex; uniform sampler2D uSplatTex;
uniform int uMode; uniform bool uHasPhoto; uniform bool uHasSplat;
varying vec2 vUv;
void main() {
  vec4 col;
  if (uMode == 2) { // side-by-side
    if (vUv.x < 0.5) col = uHasPhoto ? texture2D(uPhotoTex, vec2(vUv.x*2.0, vUv.y)) : vec4(0.2,0.2,0.2,1.0);
    else col = uHasSplat ? texture2D(uSplatTex, vec2((vUv.x-0.5)*2.0, vUv.y)) : vec4(0.2,0.2,0.2,1.0);
    if (abs(vUv.x - 0.5) < 0.002) col = vec4(0.8,0.8,0.8,1.0); // divider
  } else if (uMode == 1) {
    col = uHasSplat ? texture2D(uSplatTex, vUv) : vec4(0.2,0.2,0.2,1.0);
  } else {
    col = uHasPhoto ? texture2D(uPhotoTex, vUv) : vec4(0.2,0.2,0.2,1.0);
  }
  gl_FragColor = col;
}
```
Plane geometry UVs already map image-top to +Y (PlaneGeometry default). The splat render target texture may need `texture.flipY = false` (render targets are not flipped by default in Three.js, unlike image textures) — handle per-texture; verify orientation during implementation and flip if the splat view appears upside-down. Photos use `texture.colorSpace = SRGBColorSpace`; splat render-target texture is already sRGB (Spark forces `SRGBColorSpace` on its target). Set `renderer.outputColorSpace = SRGBColorSpace`.

Each plane stores both textures and updates `uMode` when the global mode changes. A global `let imageMode = 0/1/2` drives all planes; `applyImageMode()` traverses image planes and sets `material.uniforms.uMode.value`.

### UI: 3-way control
Add to the panel under a new **"Image"** section (between Elements and Convention):
```
Image
  ( ) photo
  (•) splat
  ( ) both
```
Three radio buttons (`name="imgmode"`, `value=photo|splat|both`). Default `photo`. Change event → set `imageMode` (0/1/2) → `applyImageMode()`.

When `?splat` is absent, the splat/both radios still work but planes show the gray placeholder via `uHasSplat=false`. Optionally disable the splat/both radios when no splat URL — but keep it simple: just show placeholder.

### `rebuildCameras()` integration
`rebuildCameras()` (already exists for the flipYZ toggle) rebuilds frustum + image-plane nodes. It must now also (re)attach the two textures and the ShaderMaterial to each image plane, and call `applyImageMode()` at the end so the current mode is honored after a rebuild. The splat textures are computed once at load (independent of flipYZ) — BUT the offscreen camera pose depends on `flipYZ` (the c2w conversion), so toggling flipYZ would invalidate the splat renders. Decision: **splat renders are computed once with the initial `flipYZ` value and not recomputed on flip toggle** — the splat view is "what the camera sees" in the original convention; re-rendering on every flip toggle is expensive and the flip is really for the 3D frustum display convention. Document this: if you toggle flipYZ after splat views are baked, the splat textures remain from the original convention (a note in the panel or code comment). This keeps the toggle cheap. (If the user wants splat views re-baked, they reload the page with the desired flip default — could add a "re-bake splat views" button later, out of scope.)

### Loading flow (updated)
1. Show loading spinner.
2. `Promise.all`: load 3 JSONs (store `allFrames`), fetch+parse `points3d.ply` (optional).
3. If `?splat` present: `new SplatMesh({ url })`, `await splat.initialized`. Add to `splatScene` at identity pose.
4. `rebuildCameras()` (builds frustums + image planes with ShaderMaterial, attaches photo textures).
5. If splat loaded: pre-render all 64 views → store `splatTextures`. Update loading label with progress.
6. `applyImageMode()` (default photo), `applyVisibility()`, `autoFrame()`, hide loading.
7. The main `setAnimationLoop` continues rendering the **view** scene (cameras + points) to the canvas as before. The splat scene is only ever rendered offscreen during step 5, never in the live loop (so toggling modes is instant — just a uniform change).

### Coordinate summary (for the splat render)

- Splat at identity in `splatScene` → same world frame as cameras (per user's "same frame" choice).
- Vertical FOV derived from `camera_angle_x` + aspect so the captured view matches each camera's intrinsics.
