## Camera Viewer Module — Implementation Plan

Deliver a standalone, self-contained Three.js HTML page that reads the Nerfstudio-style `transforms_*.json` files under `E:\Code\TripoSplat\static\000000\mvs\` and renders every camera's intrinsics + extrinsics, plus the sparse point cloud and world helpers.

### New file
`static/cam_viewer/cam_viewer.html` (single file, ~300–400 LOC, ES module via importmap — no build step, no backend code).

`run_gradio.py` and `triposplat.py` are **not** modified. The page is served with any static file server (documented below) and also works through Gradio's `/gradio_api/file=` scheme via a `?base=` query param.

### How assets are located
- The page reads a `?base=<URL-of-mvs-folder>` query param.
- Default (when `?base=` omitted): `new URL('../000000/mvs/', location.href)` — so running `python -m http.server --directory static` and opening `http://localhost:8000/cam_viewer/cam_viewer.html` works out of the box (HTML at `/cam_viewer/`, mvs at `/000000/mvs/`).
- All fetches resolve against `base`: `${base}/transforms_train.json`, `${base}/transforms_val.json`, `${base}/transforms_test.json`, `${base}/points3d.ply`, `${base}/images/NN.png`.

### Three.js setup (matches existing `viewer.html` conventions)
- Same importmap: `three` → cdnjs r0.180.0, `three/addons/` → unpkg `three@0.180.0/examples/jsm/`. (No Spark.js needed here.)
- Same visual style: radial-gradient background `#1a2035→#080b12`, HUD `#94a3b8` 12px system-ui top-left, a `#loading` spinner block and `#error` block matching the existing CSS.
- `OrbitControls` (damping 0.07, min/max distance 0.1–200), viewing `PerspectiveCamera(50, …, 0.01, 1000)`, `WebGLRenderer({antialias:true})`, resize listener, `setAnimationLoop`.

### Coordinate convention (the key correctness point)
Nerfstudio `transform_matrix` is **camera-to-world** in OpenCV local convention (+X right, +Y down, +Z forward). Three.js camera-local is (+X right, +Y up, -Z forward). The conversion is a 180° rotation about X that flips Y and Z:

`M_threejs_c2w = M_nerfstudio_c2w · S`, where `S = diag(1, -1, -1, 1)`.

Implemented as: build `Matrix4` from the flattened 4×4 `transform_matrix`, then `.multiply(S)` (post-multiply), then feed into a per-camera `Object3D.matrix` with `matrixAutoUpdate=false`. Both frustum and image plane are defined in this converted local frame and inherit the correct world pose. A short comment in the file documents the derivation.

The scene world up defaults to +Y (Three.js native). A UI toggle "Up axis: Y / Z" rotates the scene root Group by ±90° about X for datasets stored Z-up. Default Y-up.

### Per-camera rendering
For each frame, intrinsics read **per-frame** (fl_x/fl_y/camera_angle_x/camera_angle_y vary frame-to-frame and override the top-level defaults; w/h/cx/cy are constant but read per-frame anyway for safety). `file_path` values are extension-less (`images/02`) → append `.png` to load the photo.

Each camera becomes one `Object3D` (the c2w) containing:
1. **Wireframe frustum** (`LineSegments`, `LineBasicMaterial`): apex at local origin, image plane at `z = -d` where `d` is a configurable frustum scale (default 0.5 world units). Corners at `(±half_w, ±half_h, -d)` with `half_w = d·tan(camera_angle_x/2)`, `half_h = d·tan(camera_angle_y/2)`. Draw 4 apex→corner rays + 4 corner→corner rim edges (8 segments). Apex marked with a small sphere.
2. **Textured image plane** (`PlaneGeometry(2·half_w, 2·half_h)` at `z = -d`, `MeshBasicMaterial` with the loaded PNG as `map`, `side=DoubleSide`, slightly translucent): gives an intuitive sense of each camera's footprint. PlaneGeometry default UVs + `texture.flipY=true` (default) map image-top to +Y, matching the converted local frame — verified during implementation, flipped if needed.

Color coding by split: **train = #60a5fa (blue)**, **val = #34d399 (green)**, **test = #fb923c (orange)**. Wireframe material color = split color; image planes keep the photo but a thin colored rim line disambiguates the split.

### Sparse point cloud (`points3d.ply`)
A minimal inline PLY parser (~60 LOC): read the ASCII header line-by-line until `end_header`, capture `format` (ascii / binary_little_endian / binary_big_endian) and the ordered vertex properties. Parse `x, y, z` and optional color (`rgb` or `red,green,blue`, normalized to 0–1). Build a `BufferGeometry` + `THREE.Points` with `PointsMaterial({ size: 0.01, vertexColors: hasColor, sizeAttenuation: true })`. If no color property, fall back to a uniform `#9ca3af`. Handles both ASCII and binary PLY (the 2.7 MB file is likely binary).

### World helpers
- `AxesHelper(0.5)` at origin.
- `GridHelper(10, 20)` on the XZ plane (fades nicely with the dark bg).
- Both toggled via the UI.

### UI overlay panel (top-right, matches HUD styling)
A compact `<div>` with checkboxes:
- Splits: `train` / `val` / `test` (each with a color swatch), toggling visibility of that split's `Group`.
- Elements: `frustums` / `image planes` / `point cloud` / `axes` / `grid`.
- `Up axis: Y / Z` radio.
- A one-line status: `train: 30 · val: 2 · test: 32 · points: N`.

Toggles set `.visible` on the corresponding `Group`/objects — no re-upload.

### Loading flow
1. Show loading spinner.
2. `Promise.all` fetch the three JSONs + `points3d.ply` (HEAD for size label, like the existing viewer).
3. Parse JSONs → build per-split `Group`s of camera `Object3D`s.
4. Parse PLY → add points.
5. Load 32 image textures (parallel `TextureLoader`); image planes appear as textures arrive (transparent until loaded). 32 small PNGs is light.
6. Auto-frame: compute `Box3` over the point cloud (or camera apexes if no cloud), set `OrbitControls.target` to its center and place the viewing camera at `center + (0, 0.3·size, 1.6·size)`.
7. Hide loading. 4s fallback timeout like the existing viewer.
8. On any fetch/parse error → show the red `#error` block with the message.
